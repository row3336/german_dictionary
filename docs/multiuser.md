# Multiuser режим — дизайн, объём, риски

> Рабочий документ по переводу бота из owner-only в мультиюзер. Сюда складываем
> всё обсуждение. Заземлено на код по состоянию ветки `refactor/split-main-stage1`
> (2026-06-23). Ссылки вида `файл:строка` — на момент написания.

---

## 1. Решение: ОДИН продукт, не раздваивать

Раньше рассматривался форк: отдельно «мой» бот + отдельно «подарочный» для знакомых.
**Решено делать один продукт** (общий core + общая БД слов + per-user состояние).

**Почему:** любая доработка/багфикс в форке пришлось бы делать дважды → двойная
стоимость поддержки и неизбежный дрейф двух кодовых баз. Один продукт с owner-гейтингом
дешевле в сопровождении.

## 3. Состояние архитектуры СЕЙЧАС (факты из кода)

Хорошая новость: **дата-слой уже на ~80% мультиюзерный.** Самая сложная часть
(per-user интервальное состояние) уже сделана с правильными композитными ключами.

### ✅ Уже per-user (есть `user_id`, корректные PK/индексы)
- `progress` — `PK(user_id, word_id, mode)` — FSRS-состояние (`storage.py:122`)
- `form_stats` — `PK(user_id, word_id)` — weak-моды (`storage.py:173`)
- `quiz_events` — `user_id` — статистика/ретеншн (`storage.py:156`)
- `learning_items` / `learning_batches` — `user_id` (`storage.py:349/360`)
- `transaction_log` — `user_id` — undo (`storage.py:375`)
- `word_flags` — `user_id` (`storage.py:140`)
- `user_levels` — `PK(user_id, level)` (`storage.py:274`)
- `users` — `PK(user_id)` + колонки `username, first_name, status, interface_lang, dict_lang, created_at, updated_at` (`storage.py:258`)

### ✅ Shared — и это правильно (один словарь на всех)
- `words` — общий словарь, наполняет только owner
- `synonym_groups` / `word_synonyms` — общие
- `banned_words` — общие

### ⚠️ Глобальное, а ДОЛЖНО стать per-user — главный рефактор
- `app_settings` — `(key TEXT PRIMARY KEY, value)` — **глобальная** таблица «ключ→значение»
  без `user_id` (`storage.py:269`). Здесь живут ВСЕ настройки: язык
  (`owner_interface_lang`, `owner_dict_lang`), FSRS/retry (`session_retry_*`), `topic_filter`,
  drill, learning-параметры, а также owner-only (`vf_*`, `auto_dump_mode`, `fsrs_report_*`).
- `get_setting` / `set_setting` (`storage.py:1734/1747`) — ключ без user_id. Вызываются
  **повсюду** → это самый широкий blast radius рефактора.

### 🌀 Vestigial: per-user инфра уже построена, но ОТКЛЮЧЕНА
Похоже, осталось от ранней попытки мультиюзера (как осиротевший `LEVELS_MENU` из todo):
- `users.interface_lang` / `users.dict_lang` — колонки есть.
- `set_user_interface_lang` / `set_user_dict_lang` / `get_user_languages` /
  `ensure_default_languages_for_existing_users` / `_ensure_default_user_levels`
  (`storage.py:1660–1732`) — функции есть.
- **НО** живые хелперы `_user_interface_lang(user_id)` / `_user_dict_lang(user_id)`
  (`common/lang.py:10/16`) **игнорируют `user_id`** и читают глобальные owner-ключи из
  `app_settings`. То есть точка подключения per-user языка уже есть — её просто надо
  «воткнуть» в таблицу `users`. **Низкий риск.**

### Модель соединения с SQLite (важно для §6)
- `sqlite3.connect(path)` на каждый вызов, контекст-менеджер `_connect` (`storage.py:41`).
- **НЕТ** `PRAGMA journal_mode=WAL`, **НЕТ** `busy_timeout`, дефолтный rollback-journal.
- Вызовы БД **синхронные** внутри async-хендлеров → блокируют event loop на время операции.
- Бот — **один процесс, один event loop**, `run_polling`.

## 4. Объём работ по областям (с оценкой риска)

Риск: 🟢 низкий (аддитивно/изолированно) · 🟡 средний (трогает много мест, но механически) · 🔴 высокий (тихие баги корректности).

1. 🟡 **Owner-гейтинг add/AI.** Закрыть состояния `ADD_*` и `send_learn` за `is_owner`,
   спрятать кнопки (в `ui/keyboards.py` ветвление по `is_owner` уже есть — `:122/133/144`).
   Риск средний: FSM-входы общие для всех, надо аккуратно перекрыть и кнопки, и хендлеры.
2. 🔴 **Per-user настройки — ядро.** Рекомендация: **не** ломать `app_settings`, а завести
   отдельную `user_settings(user_id, key, value, PK(user_id,key))` + геттер
   `get_user_setting(user_id, key, default)` с фолбэком на дефолт. Owner-only глобалы
   (`vf_*`, `auto_dump`, `fsrs_report_*`) остаются в `app_settings`. Чёткий раздел
   «персональное / глобальное» — меньше churn, меньше шанс перепутать.
3. 🟢→🟡 **Per-user язык меню + режим словаря.** Инфра уже есть (§3 vestigial) — подключить
   `common/lang.py` к `users`-таблице вместо owner-ключей + UI выбора (есть `SELECT_*_LANG`).
4. 🟡 **Per-user алгоритм + «сброс к дефолту».** Ложится на #2 (user_settings). Кнопка reset =
   удалить per-user строки → фолбэк на дефолты.
5. 🔴 **clarify_fields: `example`/`image` для гостя как override + «предложить правку».**
   Гость **не должен** писать в общий `words` (испортит всем). Два варианта:
   (а) per-user override-таблица `user_word_media(user_id, word_id, image, example, PK(user_id,word_id))`
   + `COALESCE` при чтении (идея уже в todo); (б) очередь предложений на ревью владельцу.
   Владелец просил «кнопку предложить правку» → скорее (б), либо (а)+(б).
6. 🟢 **«Репорт ошибки» в квизах + трассировка.** Аддитивно: писать в таблицу (как `word_flags`)
   `user_id + word_id + mode + state + last_action` и уведомлять владельца. Стыкуется с уже
   внедрённым `add_error_handler` (можно переиспользовать логирование контекста).
7. 🟢 **«Фидбек» в настройках.** Аддитивно: таблица предложений + уведомление владельцу.
8. 🟢 **Донат звёздами (Telegram Stars).** Полностью изолированно: `sendInvoice` с валютой `XTR`
   + payment-хендлеры (PTB поддерживает). На будущее, не трогает существующие потоки.
9. 🟡 **Регистрация юзеров.** Проверить, что `start` для НЕ-owner создаёт строку в `users`
   (функции записи есть — `storage.py:1522+`), назначает дефолтные язык/настройки/levels.

## 5. Слабые места / риски «что-то сломается» (по убыванию опасности)

1. 🔴 **Cross-user утечка данных в SELECT-ах.** Главный тихий риск. Любой запрос, забывший
   `WHERE user_id = ?`, смешает прогресс/статистику разных людей. Прецедент уже был
   (в `select_due` — «защита от бага порядка параметров», см. историю). **Нужен аудит всех
   SELECT в `storage.py`**, что каждый per-user запрос фильтрует user_id. Тихо, не падает —
   именно поэтому опасно.
2. 🔴 **Гость пишет в общий `words`.** Если clarify/правку гостя случайно направить в `words`,
   повредятся данные всех. Обязательно через override-таблицу или очередь предложений (§4.5).
3. 🟡 **FK-каскады на общем `words`.** `PRAGMA foreign_keys=ON`. Когда owner удаляет/правит
   слово — проверить, как это влияет на `progress`/`form_stats`/`learning_items` ВСЕХ юзеров
   (каскадное удаление per-user прогресса? сирота?). Нужен явный разбор `ON DELETE`-поведения.
4. 🟡 **Blast radius per-user настроек.** `get/set_setting` зовётся повсюду; путаница
   «глобальное vs персональное» даст либо протечку чужих настроек, либо потерю своих.
   Митигация — отдельная `user_settings` (§4.2), а не правка глобальной таблицы.
5. 🟡 **Джобы/напоминания — owner-only.** `get_owner_id()` в `jobs/reminders.py:103`,
   `jobs/reports.py:105/170`, `jobs/auto_dump.py:20`. Для мультиюзера напоминания надо либо
   оставить owner-only (безопасно для старта), либо рассылать всем — а это упирается в лимиты
   Telegram (§6) и требует троттлинга.
6. 🟢 **FSM-изоляция между юзерами — уже ОК.** PTB ключует `context.user_data` по user_id
   автоматически → состояние диалогов изолировано без работы. Модульные дикты
   `VF_RUNNING_TASKS`/`VF_STOP_FLAGS` тоже ключованы по user_id. Здесь риска нет.

**Вердикт по риску:** перевод МЕНЕЕ рискован, чем мультиюзер с нуля, потому что тяжёлая часть
(per-user интервальное состояние) уже сделана и проиндексирована. Основная опасность — не
«большая переписка», а **тихая корректность**: изоляция user_id в запросах (#1) и недопущение
записи гостя в общий словарь (#2). Эти два — под обязательный аудит/тесты перед мержем.

## 6. Нагрузка и масштабирование (если юзеров больше, чем думалось)

### Как устроено сейчас
- **Один процесс, один event loop.** Параллелизма ядер нет.
- **Синхронные вызовы SQLite внутри async** → каждая операция БД **блокирует весь бот** на
  своё время. При 1 юзере незаметно; при N одновременных — все ждут друг друга.
- **Нет WAL + нет busy_timeout** → дефолтный rollback-journal берёт эксклюзивную блокировку на
  запись. Две одновременные записи (двое ответили на квиз в одну и ту же ~10мс) → **`database
  is locked` (SQLITE_BUSY)** немедленно, без ожидания → упавшее действие (сейчас его подхватит
  новый `add_error_handler` → «повтори», но действие всё равно сорвётся).

### Реалистичная оценка для «подарочного» бота
Друзья/знакомые = ориентировочно единицы–десятки юзеров, и **редко строго одновременно**.
SQLite такое тянет тривиально — **при условии**, что добавим базовую устойчивость к
конкуренции. Объём данных тут вообще не проблема (БД на тысячи слов × десятки юзеров — копейки).

### Что делать ДО мультиюзера (дёшево, большой выигрыш надёжности)
Базовая защита от блокировок — пара PRAGMA в `_connect`:
- `PRAGMA journal_mode=WAL` — писатели не блокируют читателей.
- `PRAGMA busy_timeout=5000` — при конкуренции ждать до 5с, а не падать сразу.
- `PRAGMA synchronous=NORMAL` — безопасно при WAL, быстрее.

Это снимает подавляющее большинство `database is locked` на ожидаемой нагрузке. **Рекомендуется
внедрить даже до мультиюзера** (полезно и сейчас при джобах + квизах одновременно).

### Где реально начнёт ломаться (потолок)
- **SQLite = один писатель.** Если когда-нибудь будет много **активно одновременно пишущих**
  юзеров (сотни в одни и те же секунды) — даже с WAL начнёшь упираться: записи сериализуются.
- **Синхронная БД в loop.** Под высокой конкуренцией блокировки event loop начнут давать
  заметные задержки всем (тот же класс симптомов, что и сетевые задержки, но уже от БД).
- Это **далеко за пределами «друзей»**. Симптомы при приближении: рост `database is locked`
  в логах, общая «вязкость» откликов под пиком.

### Путь миграции (когда/если упрёшься — НЕ сейчас, преждевременно)
1. Вынести вызовы БД из event loop в тред-пул (`asyncio.to_thread`) — убирает блокировку loop.
2. При действительно большой нагрузке — перейти на Postgres (настоящий конкурентный доступ,
   несколько писателей). Схема почти переносима (композитные PK/индексы уже есть).

### Сторона Telegram
- При **рассылке напоминаний всем** юзерам упираешься в глобальный лимит ~30 msg/s (flood
  limit). Уже внедрённые `_reply_text_with_retry` + `add_error_handler` смягчают, но рассылку
  надо **троттлить** (очередь с задержкой), а не слать пачкой. Учесть при дизайне §4.6/джобов.

## 8. Рекомендуемый порядок внедрения (черновик)

1. **Базовый PRAGMA WAL + busy_timeout** (полезно уже сейчас, фундамент под конкуренцию).
2. **Аудит изоляции user_id** во всех SELECT + тесты на cross-user (страховка корректности).
3. **`user_settings` + per-user геттер** (фундамент под персональные настройки).
4. **Per-user язык/режим словаря** (инфра почти готова — быстрый видимый результат).
5. **Owner-гейтинг add/AI** + регистрация гостей в `users`.
6. **Per-user алгоритм + reset-to-default.**
7. Аддитивные фичи: **репорт ошибки**, **фидбек**, **предложить правку** (override/очередь).
8. **Донат звёздами** — последним, изолированно.
